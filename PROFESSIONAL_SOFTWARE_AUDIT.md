# Pharmacy ERP — Professional Software Audit

**Audit date:** 4 November 2026  
**Workspace version:** 3.4.0+1 (from `pubspec.yaml`)  
**Scope:** Flutter desktop pharmacy ERP source, SQLite persistence, Supabase REST/RPC/Realtime code, SQL setup/migration scripts, stock and batch logic, LAN sync, backups, and static analyzer output.

## Executive assessment

The project has meaningful foundations: sales and purchase saves use local SQLite transactions, an offline outbox exists, server RPCs aim to apply stock atomically, the app has reconnect/delta sync, and the backup service can make and integrity-check a local SQLite snapshot. Those are useful building blocks.

**The code cannot currently be certified as safe for production or “100% correct.”** The static review found release-blocking risks in database access policy, the atomic stock RPC, duplicate cloud submission paths, and inconsistent local stock representations. These can expose customer/business records or cause cloud stock to diverge from local stock. Fix and verify the Critical/High items before relying on the system for multiple PCs or live pharmacy inventory.

This is a code/configuration audit, not a live Supabase penetration test or an observed multi-PC acceptance test. The repository's `supabase_schema_dump.json` is empty; `supabase_analysis_results.json` has no audit provenance/date; therefore the actual deployed schema, RLS policies, function privileges, and migration state remain unverified. The older `AUDIT_REPORT.md` is dated 2 November and says version 3.3.7, while the current package is 3.4.0+1, so its findings were not assumed current.

## Findings: current system, professional standard, recommendations

### Critical — resolve before production use

| 1. My current system | 2. How professionals do it | 3. Recommendations |
|---|---|---|
| **[Critical] Database access is configured as open.** The Supabase setup SQL enables RLS, creates an `Allow All Access` policy with `USING (true) WITH CHECK (true)` for `anon, authenticated, service_role`, and grants all table/sequence privileges to those roles. Similar SQL is embedded in the app service. The stock convergence SQL also creates `SECURITY DEFINER` mutation RPCs without visible per-function privilege revokes; PostgreSQL normally grants `EXECUTE` to PUBLIC unless default privileges override it ([PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html)). If deployed with the bundled anon key, unauthenticated clients may be able to read or change pharmacy data, subject to live Supabase/project settings. See [setup script](lib/database/setup_supabase_server_master_script.sql#L264), [embedded setup SQL](lib/services/supabase_sync_service.dart#L7860), [stock RPC](lib/database/stock_convergence_master.sql#L217), and the [default key configuration](lib/services/server_config_service.dart#L47). | Default-deny RLS with a real authenticated identity, tenant/branch membership checks on every row, least-privilege table/function grants, and no anonymous access to patient, sales, purchase, payment, or stock records. `SECURITY DEFINER` functions are explicitly revoked from PUBLIC and granted only to intended roles. | **Treat as P0.** Do not deploy the allow-all script. Inspect the live project’s RLS policies and grants now. Replace broad policies with per-table branch/tenant policies tied to authenticated users. Revoke PUBLIC/anon execution on privileged functions and grant narrowly. Keep service-role credentials server-side only. |
| **[Critical] Stock RPC lock query is invalid PostgreSQL.** `fn_process_sale_atomic` selects `SUM(current_quantity)` and appends `FOR UPDATE` in the same aggregate query ([SQL](lib/database/stock_convergence_master.sql#L290)). The same pattern appears in other stock RPC checks. PostgreSQL disallows row-lock clauses with aggregate queries; the atomic RPC will error at that statement instead of protecting the stock check. [PostgreSQL SELECT documentation](https://www.postgresql.org/docs/current/sql-select.html) | Lock the actual matching batch rows in a deterministic order, then calculate availability within that transaction. Protect the set from concurrent changes with an appropriate uniqueness/locking strategy and enforce nonnegative stock in the database. | **Treat as P0.** Rewrite every aggregate-plus-lock check. Validate each RPC against the actual Supabase PostgreSQL version, then concurrently sell the last available units from two clients and assert only one succeeds and the ledger/balance agree. |
| **[Critical] A single sale or purchase can be sent to Supabase through two independent write paths.** Local save queues an outbox operation; queueing immediately starts an unawaited drain when connected. The same save then calls direct RPC/REST sync. The outbox and direct sync each generate timestamp-based idempotency keys, so they are different keys and the server cannot deduplicate the two attempts. See [outbox enqueue/auto-drain](lib/services/stock_outbox_service.dart#L137), [sale save dispatch](lib/providers/pharmacy_provider.dart#L9140), [purchase save dispatch](lib/providers/pharmacy_provider.dart#L9621), [purchase RPC key generation](lib/services/supabase_sync_service.dart#L1528), and [sale RPC key generation](lib/services/supabase_sync_service.dart#L3001). | One durable transactional outbox is the only client-to-server mutation path. A document operation has a stable identity and revision; retries reuse that key. Server-side invoice edits/voids reverse old stock effects and apply new effects atomically. | **Treat as P0.** Remove the duplicate direct push when the outbox owns delivery. Persist the outbox record in the same SQLite transaction as the voucher and local stock changes. Use one stable idempotency key for a voucher revision. Make edit/void a distinct atomic server operation that reverses prior ledger effects before applying replacements. |
| **[Critical] The same invoice edit can be applied as a fresh stock movement.** The local save code replaces/reverses old invoice effects, but the cloud sale RPC’s idempotency is keyed by a timestamp-generated request key and applies stock deductions for each accepted call. Editing/resaving a voucher creates another key; the SQL upserts the invoice but does not visibly reverse its prior cloud stock movement before applying new items. Duplicate path above makes the risk higher. See [local sale edit flow](lib/providers/pharmacy_provider.dart#L8766), [cloud stock RPC](lib/database/stock_convergence_master.sql#L215), and [direct RPC key](lib/services/supabase_sync_service.dart#L3001). | Financial documents are immutable after posting or changed through a versioned correction/reversal transaction. The server records one ledger effect per document version and rejects stale/conflicting edits. | Make edits, cancellations, returns, and voids explicit server transactions with old/new line comparison and immutable movement records. Reconcile document revision and stock ledger in the same server transaction. |

### High — inventory, sync, and multi-PC reliability

| 1. My current system | 2. How professionals do it | 3. Recommendations |
|---|---|---|
| **[High] Two local stock models coexist.** The database creates both `stock_batches` (mutable `current_stock`) and `batch_master` plus `stock_ledger`. The primary sales path changes `stock_batches.current_stock`; newer `StockService` computes live stock from ledger rows joined by `batch_master.batch_id`. Another helper writes a batch number into the ledger’s `batch_id`, while the newer repository expects a generated `batch_id`. These paths can report different quantities for the same product. See [SQLite schema](lib/database/db_helper.dart#L733), [legacy stock schema](lib/database/db_helper.dart#L1582), [sale stock deduction](lib/providers/pharmacy_provider.dart#L8900), [ledger writer](lib/database/db_helper.dart#L2810), and [ledger repository](lib/repositories/stock_repository.dart#L10). | One canonical inventory model: unique branch/product/batch identity, immutable movement ledger, derived balance, and a clear authority for local/offline versus server state. All workflows (sale, purchase, returns, damage, adjustments, reconciliation) use the same domain service. | Choose one batch/ledger model. Migrate and reconcile existing rows with a repeatable migration, then route every stock-changing operation through one transaction service. Add invariants comparing document-derived quantities, ledger balance, and displayed batch balance. |
| **[High] Quantity units differ across paths.** The local sale path deducts `item.qty`; its LAN payload multiplies `(qty + fQty) * packin`; the cloud sale RPC computes `qty + f_qty` without using `packing`. Purchase code uses `(qty + fQty) * packin` locally. This can create different stock totals depending on which path processes the voucher. See [local sale](lib/providers/pharmacy_provider.dart#L8920), [LAN sale event](lib/providers/pharmacy_provider.dart#L9130), [purchase local stock](lib/providers/pharmacy_provider.dart#L9233), and [cloud sale RPC](lib/database/stock_convergence_master.sql#L279). | Every stock quantity is converted once to a documented base unit (for example loose tablets) at the domain boundary. API fields distinguish pack quantity, loose quantity, pack size, and base-unit delta. | Define the canonical unit and formulas for all entries. Normalize payloads before persistence; use shared conversion logic on local, LAN, and server paths. Test pack sizes 1 and >1, loose quantities, split batches, edits, returns, and fractional/invalid input. |
| **[High] The FEFO helper can include expired stock and sorts mixed date formats inconsistently.** It filters active/positive stock but has no expiry cutoff. Its ordering specially parses slash-formatted dates and gives all other formats a fallback sort key; the model writes ISO dates. See [batch selection](lib/repositories/stock_repository.dart#L120). | FEFO uses one validated date representation, excludes expired/invalid batches by default, and requires a logged, permissioned override to dispense expired stock where legally permitted. | Store expiry as a typed date/ISO value, normalize legacy values during migration, and make batch allocation reject expired/invalid stock. Add tests for ISO, slash, month/year-only, end-of-month, and expired dates. |
| **[High] Batch fallback can merge different lots.** `findOrCreateBatch` first checks batch number plus expiry/rates, but if that fails it falls back to product plus batch number only and returns the newest match. A reused manufacturer batch number with a different expiry, price, or supplier can be merged into the wrong lot. See [batch matching](lib/repositories/stock_repository.dart#L46). | A lot’s identity includes a defined set of fields, commonly branch, product, normalized batch number and expiry; new lots are not silently merged when material attributes conflict. | Remove the broad fallback. Define a unique batch key and reject or explicitly reconcile conflicting lot metadata instead of silently returning another lot. |
| **[High] Outbox entries can get stuck forever after a process crash.** The drain selects only `pending` and `retryable` rows, but marks work `in_flight`. A crash after that update leaves the item out of subsequent drains. See [selection](lib/services/stock_outbox_service.dart#L244) and [in-flight transition](lib/services/stock_outbox_service.dart#L265). | Durable queues use a lease/claim timestamp, reclaim expired work after restart, bounded exponential backoff with jitter, attempt limits, and a visible dead-letter/replay workflow. | Reclaim stale `in_flight` rows at startup and before drain. Add lease expiry, jittered backoff, max attempts, operator-visible rejection/dead-letter details, and safe replay using the same idempotency key. |
| **[High] Realtime and LAN are treated as fast delivery mechanisms; the recovery guarantee is unclear.** Realtime listeners and a delta catch-up exist, which is good, but the LAN service sends UDP broadcasts and TCP data without acknowledgements or durable peer offsets. UDP may lose or reorder packets; product chunks are sent as large JSON datagrams. Listener dedup marks events asynchronously. See [LAN transport](lib/services/lan_sync_service.dart#L88) and [bulk transfer](lib/services/lan_sync_service.dart#L210), [Realtime subscriptions](lib/services/supabase_realtime_service.dart#L340), and [delta sync](lib/services/delta_sync_service.dart#L28). | Realtime/UDP signals are hints; durable server state or a persisted ordered event log is the source of truth. Bulk data uses a reliable transport with acknowledgements, resume offsets, checksums, and schema versioning. | Keep LAN payloads small and non-authoritative. For bulk transfers use authenticated TCP/HTTPS with chunk acknowledgement and resumable transfer. Make reconnect catch-up compare durable server cursors, not just transient events. |
| **[High] LAN sync has no peer authentication or encryption and sends customer details.** UDP/TCP listeners bind on all IPv4 interfaces. A sale event includes patient name and invoice amount; incoming payloads are accepted based on a sender hostname string. See [LAN bind and sender check](lib/services/lan_sync_service.dart#L88) and [sale event payload](lib/providers/pharmacy_provider.dart#L9120). | Peer identity is cryptographic, traffic is encrypted, messages are authenticated and replay-protected, and sensitive records are not broadcast. | Stop broadcasting PII. Prefer sending only an invalidation/document ID and fetch authorized details from the server. If LAN transfer remains, require authenticated encrypted sessions and validate signed event IDs, branch, terminal, version, size, and replay window. |
| **[High] REST fallback writes header and child rows in separate requests.** Some fallback paths upsert a header, delete existing child items, then insert items; delete results can be ignored. A failure can leave a header with missing/partial children or a retry that replaces children after the header was accepted. See [sale REST fallback](lib/services/supabase_sync_service.dart#L3040) and [purchase REST path](lib/services/supabase_sync_service.dart#L3170). | Multi-table vouchers are created/edited through one database transaction/RPC. The client marks a voucher synced only after the server confirms the full transaction. | Remove multi-request mutation fallbacks for financial documents. Use atomic RPCs only; if unavailable, keep the voucher pending and show a clear sync error. Add a server-side reconciliation report for parent/child completeness. |
| **[High] Schema and deployment scripts can diverge.** The project has multiple setup scripts and an embedded SQL installer. One script installs broad allow-all RLS; another drops policies and creates a deny policy for authenticated users. The supplied schema-diff JSON reports missing columns/tables but has no freshness/provenance, and the schema dump is empty. | Database migrations are versioned, reviewed, applied once through CI/CD, and checked against a known schema version. RLS and function permissions have automated policy tests. | Establish one canonical migration history. Remove embedded/manual duplicate schema installers. Add a startup compatibility check and a staging migration gate. Regenerate the schema diff from a known live project with timestamp and project identity before treating any listed mismatch as current. |
| **[High] Offline voucher numbering needs stronger conflict controls.** Online sequence claims are attempted but failures are swallowed; local fallback creates a terminal-prefixed offline number. A robust reconciliation path is not established by this audit. See [sale sequence allocation](lib/providers/pharmacy_provider.dart#L8780) and [offline fallback generation](lib/providers/pharmacy_provider.dart#L9730). | Numbering rules are enforced server-side with a unique key scoped by branch and financial year. Offline IDs are globally unique and later mapped to legal invoice numbers without rewriting audit history. | Confirm global uniqueness constraints and collision handling on the live schema. Persist an immutable local UUID; assign the legal document number centrally when online. Test two offline PCs reconnecting with overlapping sequence state. |

### Medium — controls, operations, and maintainability

| 1. My current system | 2. How professionals do it | 3. Recommendations |
|---|---|---|
| **[Medium] The product has transaction-level checks, but important invariants need to be enforced beyond the UI.** `saveSale` checks account/patient/doctor values and has stock checks, while the server functions vary in validation and payload defaults. | Critical business rules are validated in domain services and again at the server boundary: non-empty lines, valid IDs, positive integer base quantities, valid expiry, finite/decimal-safe money, required schedule/controlled-drug fields, and branch ownership. | Create a shared validation contract and reject invalid payloads before local commit. Enforce equivalent constraints in server RPCs and database constraints; never let the UI be the only guard. |
| **[Medium] Money fields and calculations use Dart `double` and SQLite REAL in key paths.** Currency formatting helpers exist, but binary floating-point can produce rounding inconsistencies when values are repeatedly discounted/taxed/rounded. | Financial amounts use integer minor units or fixed-precision decimal arithmetic, with one authoritative rounding policy per jurisdiction and transaction. | Convert persisted money to integer paise (or fixed-precision NUMERIC server-side) and document rounding at line, invoice, discount, and GST boundaries. Add reconciliation cases for discounts, tax splits, round-off, returns, and edits. |
| **[Medium] Backup naming overstates off-site protection.** `CloudBackupService` makes a local file copy only. `BackupService` has a better SQLite `VACUUM INTO` snapshot, integrity check, restore, and local retention, but no demonstrated off-site encrypted copy or restore drill. See [cloud-named local snapshot](lib/services/cloud_backup_service.dart#L8) and [backup/restore](lib/services/backup_service.dart#L8). | Backups are encrypted, versioned, stored off-site in a separate failure domain, monitored, and regularly restored into a clean environment. | Rename the local-only service or implement actual off-site backup. Schedule encrypted off-site snapshots, alert on failures, maintain retention, and perform documented restore drills including pending outbox recovery. |
| **[Medium] Analyzer is clean of errors but not clean of findings.** `flutter analyze --no-pub` completed with **172 warnings/info findings**, including unused locals/fields, async BuildContext warnings, deprecated `WillPopScope`, and many control-flow style findings. Analyzer exit code was 1. | CI blocks new analyzer warnings and compile errors, with existing debt tracked and reduced incrementally. | Fix correctness/lifecycle warnings first (especially async context use), then enable analyzer in CI with a baseline or zero-new-warning policy. Re-run analysis after changes. |
| **[Medium] Business-critical code is concentrated in very large files.** Current source includes an 18,283-line provider, 12,311-line sales screen, 8,307-line purchase screen, and 7,939-line sync service. | Screens, domain operations, persistence, and sync orchestration are separated into focused modules with explicit transaction boundaries and testable dependencies. | Refactor gradually along business boundaries: sales posting, purchase posting, stock ledger, batch allocation, sync coordinator, and per-entity repositories. Keep each extraction behavior-preserving and independently verifiable. |
| **[Medium] Automated coverage is small relative to ERP risk.** Six test files exist; analyzer was run, but tests/integration/device workflows were not run as part of this audit. | Deterministic unit, database integration, server RPC, concurrency, and end-to-end workflows cover the financial and inventory paths. | Prioritize tests for the P0/P1 cases in this report. Add CI on each change and staging multi-PC acceptance tests. Do not call the software production-ready based only on analyzer success. |

## Recommended implementation order

1. **Security containment:** inspect live Supabase policies/grants; remove allow-all access and restrict privileged RPC execution.
2. **Repair server stock RPCs:** remove invalid aggregate row-lock queries; add real concurrent stock tests.
3. **Make delivery single-path:** outbox-only mutation, stable document revision keys, crash recovery for in-flight rows, and no REST multi-call fallback.
4. **Unify inventory:** choose one batch/ledger model and one base-unit convention; normalize expiry and lot identity.
5. **Prove workflow correctness:** exercise sale/purchase create, edit, retry, void, returns, adjustment, damage, offline restart, and two-PC contention against a staging Supabase project.
6. **Operational readiness:** off-site backups and restore drills, visible sync health/dead-letter handling, versioned migrations, and CI analyzer/tests.

- Ran `flutter analyze --no-pub`: **172 findings** (warnings/info), analyzer exit code 1; no analyzer errors were present in the captured output.
- Did **not** run unit tests, builds, a live Supabase migration, production data inspection, penetration testing, or a physical two-PC/offline acceptance test.

- Report confidence is highest for source-visible behavior and lower for deployed schema state, migrations already applied, and UI-only validations not called directly by the provider.
